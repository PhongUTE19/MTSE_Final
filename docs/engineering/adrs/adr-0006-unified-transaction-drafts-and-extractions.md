# ADR 0006: Unified Transaction Drafts, Immutable Extraction Audits, and Shared Confirmation Lifecycle

* **Status:** Accepted  
* **Date:** 2026-11-16  
* **Deciders:** Engineering Team, Swarm Architecture Worker  
* **Consulted:** Coordinator, Transaction Worker, Receipt Worker, Assistant Worker, Integration Worker  
* **Informed:** All Contributors  

---

## 1. Context

As SpendWise introduced multimodal receipt scanning (Gemini OCR) and a tool-calling conversational financial assistant (Gemini Function Calling), candidate transactions entered the system through three disparate pathways:

1. **Manual Entry:** Direct form input creating immediate rows in `public.expense_transactions`.
2. **Receipt Uploads:** Uploaded to Supabase Storage, processed through Gemini OCR, stored as raw JSON columns directly on `public.receipts`, and confirmed via `POST /api/receipts/:id/confirm` or discarded via `DELETE /api/receipts/:id`.
3. **Conversational Assistant Proposals:** Proposals generated by the assistant were held in an ephemeral in-memory Node.js `Map` (`proposals = new Map()`) with a 10-minute TTL, confirmed via `POST /api/expense-agent/proposals/:id/confirm` or cancelled via `DELETE /api/expense-agent/proposals/:id`.

This fragmented architecture introduced significant structural problems:
* **Server State Volatility:** In-memory assistant proposals were lost on server restarts, deployment rollouts, or multi-instance scaling, leaving users with unconfirmable proposal cards.
* **Lack of Extraction Auditability:** `public.receipts` only stored the latest extraction payload. Failed extraction attempts, retries, model versions (`gemini-2.5-flash`), and prompt template versions were neither captured immutably nor queryable.
* **Destructive Discarding:** Rejecting or discarding an extracted receipt executed a hard `DELETE` against `public.receipts` and Supabase Storage, erasing the audit trail and original document image.
* **UI Duplication & Cross-Domain Leaks:** Review and confirmation UI was split between `ReceiptReview.jsx` and `TransactionProposalCard.jsx`, duplicating VND amount validation, foreign currency conversion warnings, and line-item tables. Furthermore, `ReceiptsView.jsx` imported `expenseApi` directly, violating the 6-layer frontend boundary.
* **Unclear Manual Entry vs. AI Boundaries:** `TransactionForm.jsx` entangled manual entry with edit flows, lacking a clean separation from AI-assisted workflows.

## 2. Decision Drivers

1. **Unified Candidate Staging:** A single persistent database staging model for all candidate transactions (receipt extractions and assistant proposals) prior to committing to the immutable VND ledger (`expense_transactions`).
2. **Immutable Extraction Auditing:** Append-only history of every OCR extraction attempt (success or failure) with model and prompt provenance.
3. **Non-Destructive Rejection:** Rejecting a candidate transaction must mark the draft rejected while keeping receipt records and uploaded document files intact for accounting and tax compliance.
4. **Atomic & Idempotent Confirmation:** Prevent duplicate transactions on double clicks or network retries through atomic database claims and idempotent re-confirmation.
5. **Strict 6-Layer Architecture & Zero Cross-Feature Imports:** Unify the review UI into a reusable composite (`composites/transactions/TransactionDraftReview.jsx`), promote shared utilities to `shared/transactions/`, and manage drafts through a dedicated `features/transactionDrafts/` domain with props injected at the `app/` layer.

## 3. Considered Alternatives

* **Alternative 1: Keep In-Memory Map for Assistant & Direct-to-Table for Receipts:** Rejected because it perpetuates memory volatility, multi-container failure, and disparate confirmation pathways.
* **Alternative 2: Store Drafts Inside `public.receipts` and Create a Separate `public.proposals` Table:** Rejected because it results in schema duplication for reviewed transaction fields, validation, and confirmation endpoints.
* **Alternative 3: Unified `public.transaction_drafts` Table with Linked `public.receipt_extractions` Audit Table:** Selected because it normalizes all pre-confirmation transactions under a single lifecycle while decoupling immutable OCR attempt telemetry from mutable user-reviewed draft data.

## 4. Decision

### 4.1 Domain & Database Model (`supabase/migrations/202611160008_transaction_drafts_and_extractions.sql`)

1. **`public.receipts` (Unchanged Core Ledger):**
   - Retained with 1:1 linkage to `expense_transactions` via `transaction_id`.
   - Never deleted upon draft rejection.
2. **`public.receipt_extractions` (Immutable Extraction Audit History):**
   - Columns: `id`, `receipt_id` (FK cascade), `user_id`, `attempt` (integer >= 1), `status` (`'succeeded'` | `'failed'`), `result` (`jsonb`), `warnings` (`jsonb`), `error_code`, `ai_model`, `prompt_version`, `created_at`.
   - Unique constraint: `UNIQUE (receipt_id, attempt)`.
   - Immutability trigger: `BEFORE UPDATE` trigger raises an exception, guaranteeing write-once audit records.
   - Row-Level Security: Authenticated users can select their own; inserts restricted to `receipt_lifecycle_owner` / `service_role`.
3. **`public.transaction_drafts` (Unified Staging Model):**
   - Columns: `id`, `user_id`, `source_type` (`'receipt_extraction'` | `'assistant_proposal'`), `receipt_id` (nullable FK), `receipt_extraction_id` (nullable FK), `source_ref` (nullable text, e.g. conversation ID), `original_data` (`jsonb` normalized candidate payload, never mutated after creation), `reviewed_data` (`jsonb` user edits, null until edited), `status` (`'pending_review'` | `'confirmed'` | `'rejected'`), `transaction_id` (unique nullable FK to `expense_transactions`), `created_at`, `updated_at`, `confirmed_at`, `rejected_at`.
   - Constraints: `UNIQUE (receipt_extraction_id)` enforces at most one pending draft per extraction attempt; `CHECK` constraint validates source consistency.
   - RLS: Authenticated users can select, insert, and update their own records.
   - Note on Expiration: Assistant drafts do not auto-expire into an invalid state; they remain `pending_review` until explicitly confirmed, rejected, or patched.

> [!IMPORTANT]
> **Migration Status:** Migration `202611160008_transaction_drafts_and_extractions.sql` is authored as **LOCAL-ONLY** and must not be applied remotely without explicit database administrator approval, matching repository conventions.

### 4.2 Shared Confirmation & Rejection Workflow

1. **Atomic Claim on Confirmation:**
   - Confirmation executes an atomic claim query:
     ```sql
     UPDATE public.transaction_drafts
     SET status = 'confirmed', confirmed_at = now(), updated_at = now()
     WHERE id = $1 AND user_id = $2 AND status = 'pending_review'
     RETURNING *;
     ```
   - If zero rows are returned, the service checks whether the draft was already confirmed. If so, it returns the existing transaction (idempotent 200 OK).
2. **Ledger Commit:**
   - **For `receipt_extraction`:** Calls the existing `confirm_receipt_transaction` RPC using the user-scoped client, linking `receipts.transaction_id` and setting receipt status to `confirmed`.
   - **For `assistant_proposal`:** Inserts into `public.expense_transactions` via user-scoped RLS client.
   - The resulting `transaction.id` is linked to `transaction_drafts.transaction_id`.
3. **Safe Rejection:**
   - Executing `POST /api/transaction-drafts/:id/reject` sets `status = 'rejected'` and `rejected_at = now()`.
   - The associated receipt row in `public.receipts` and its storage file in Supabase Storage remain completely untouched.

### 4.3 REST API Endpoints

A new feature module `server/src/features/transactionDrafts/` is mounted at `/api/transaction-drafts`:

| Method | Endpoint | Description |
| :--- | :--- | :--- |
| `GET` | `/api/transaction-drafts?status=pending_review` | List current user's drafts filtered by status |
| `GET` | `/api/transaction-drafts/:id` | Retrieve single draft by ID |
| `PATCH` | `/api/transaction-drafts/:id` | Update `reviewed_data` for a pending draft |
| `POST` | `/api/transaction-drafts/:id/confirm` | Atomically claim, validate, commit to ledger, and link transaction |
| `POST` | `/api/transaction-drafts/:id/reject` | Mark draft rejected without deleting source receipt |

**Retired Endpoints:**
* `POST /api/receipts/:id/confirm` (replaced by `/api/transaction-drafts/:id/confirm`)
* `DELETE /api/receipts/:id` as user discard action (replaced by `/api/transaction-drafts/:id/reject`)
* `POST /api/expense-agent/proposals/:id/confirm` (replaced by `/api/transaction-drafts/:id/confirm`)
* `DELETE /api/expense-agent/proposals/:id` (replaced by `/api/transaction-drafts/:id/reject`)

**Enhanced Endpoints:**
* `GET /api/transactions/:id`: Enriched to include linked receipt summary (`{ id, status }`), allowing the client to request short-lived signed preview URLs (`GET /api/receipts/:id/preview`).

### 4.4 Frontend Architecture & Component Boundaries

1. **Shared Transactions Composite & Utilities:**
   - `client/src/composites/transactions/TransactionFields.jsx`: Feature-agnostic form inputs for type, amount, date, category, merchant, and note.
   - `client/src/composites/transactions/TransactionDraftReview.jsx`: Unified review, validation, foreign currency warning, line items, and confirm/reject card replacing both `ReceiptReview.jsx` and `TransactionProposalCard.jsx`.
   - `client/src/shared/transactions/`: Centralized `transactionFieldsUtils.js`, `expenseConstants.js`, and `expenseCategories.js`.
2. **Dedicated Drafts Feature:**
   - `client/src/features/transactionDrafts/`: Houses `transactionDraftsApi.js` and `useTransactionDrafts.js`.
3. **Domain Views:**
   - `client/src/features/expense/ManualEntry.jsx`: Non-AI manual entry modal/card replacing `TransactionForm.jsx`.
   - `client/src/features/expense/TransactionDetails.jsx`: Modal inspection for transactions, showing items and linked receipt summary with preview trigger.
   - `client/src/features/receipts/ScanReceiptView.jsx`: Dedicated view for uploading receipts and reviewing pending receipt drafts.
   - `client/src/features/expense/assistant/ExpenseAssistant.jsx`: Domain composition of generic `features/chat/Chatbot` and `useChat`. Renders `TransactionDraftReview` inside `ExpenseToolResult` with conversation source note. Receives upload and draft handlers via props from `app/App.jsx`.

## 5. Consequences

### Positive
* **Zero Server Memory Leaks:** In-memory proposal storage is eliminated; candidate transactions survive server restarts.
* **Complete OCR Provenance:** Every receipt extraction attempt is captured immutably with model and prompt metadata.
* **Unified Human-in-the-Loop Review:** Receipt scans and chat proposals share the exact same validation, foreign currency warning, and confirmation logic.
* **Safe Accounting Trail:** Discarding drafts does not destroy original receipt documents or images.
* **Idempotency:** Re-confirming a confirmed draft returns the existing transaction rather than generating duplicate expenses.

### Negative / Known Risks
* **Stale Test References:** Existing unit tests referencing deleted or moved files (`TransactionForm.jsx`, `ReceiptReview.jsx`, `ReceiptsView.jsx`, `TransactionProposalCard.jsx`) were intentionally left unedited per strict coordinator instruction (rule prohibiting test modifications). Updating these test files is tracked as high-priority technical debt.
* **Unapplied Migration:** The migration is local-only; staging and production databases require administrative migration execution.
* **No Runtime Browser Verification:** Verification was performed via static syntax checks (`node --check`) and client production build compilation (`npm --prefix client run build`). Interactive browser verification was not performed in this headless environment.
